# 会话切换阻塞（待排查）

## 现象

- 一个对话正在运行时，切不到另一个对话。
- 手动压缩上下文期间，同样切不了。
- 只能等当前轮结束或压缩结束，长任务和大上下文压缩时会被锁住。

## 影响

这是日常使用的主路径。多对话并行、长任务、压缩大上下文都会撞到，优先级高于一般 UI 问题。

## 初步判断

- 更像内核层的 session 串行模型，不是单纯的按钮禁用。
- 可能要大修，先定位再定方案。
- 尚未验证到具体代码路径，以下只是待查方向。

## 待查方向

1. 渲染层：切 tab 时是否被 `running` / `libraryBusy` / 压缩状态直接拦住。
2. `conversation-controller`：切换会话是否要求当前 controller 先进入 idle。
3. `DshAcpAgentClient`：一个 ACP 子进程是否只持有一个 session，切会话是否必须重建进程。
4. 压缩路径：`compact()` 期间是否持有全局锁，导致其他会话的请求排队。
5. `dsh-agent` / `agent-runtime`：`interruptTurn` 与 session 切换的先后关系。

## 验收

- 会话 A 运行中，可以直接切到会话 B 并正常发消息。
- 会话 A 在压缩时，切到 B 不排队、不报错。
- 回到 A 时，A 的流式输出和轮次状态不丢。

## 约束

- 不靠“等它跑完”绕过。
- 不破坏审批模式持久化与 ACP 连接隔离。
